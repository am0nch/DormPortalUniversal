Section 1 — Abstract & Background

Abstract Residential dormitory administration at Asia-Pacific International University (APIU) relied on a collection of disconnected Microsoft Excel spreadsheets, physical logbooks, and manual paper forms to manage student room assignments, nightly attendance, bedding sales, key issuance, incident reports, and student clearance. This fragmentation created data silos, delayed administrative responses, introduced transcription errors in cross-system reporting, and made semester-based retrospective analysis impractical. This report documents the design, development, and deployment of DormPortalUniversal v4, a browser-based, offline-capable, zero-cost integrated management system comprising 16 operational modules. The system employs a shared localStorage data layer with BroadcastChannel cross-tab synchronization, a policy-grounded data model aligned with the APIU Residence Hall Handbook (2017), and a CSV-based integration protocol with the university's SARRA2 student affairs platform. The project was completed over a six-week development period and is currently in active deployment at Elijah Hall.

1.1 Background and Institutional Context

Elijah Hall is the primary student dormitory at Asia-Pacific International University, housing residential students across four floors. The dormitory operates under policies documented in the APIU Residence Hall Handbook (1st Edition, August 2017), which specifies curfew times, fine schedules, off-campus move procedures, residency exemption categories, and other operational standards. The Dean of the dormitory and a team of Resident Assistants (RAs) carry out daily administrative functions including room reservations, nightly attendance checking, bedding distribution, key issuance, room inspection, and student clearance processing.

Prior to this project, all dormitory records were maintained in separate, unlinked Excel files with no automated cross-referencing, search functionality, or audit trail. Semester-level reporting required manual collation from multiple sources. Citizenship point deductions submitted to the university's SARRA2 student affairs system involved manual data entry from physical forms, creating a recurring source of transcription error and processing delays. Nightly attendance was recorded in paper notebooks, with no mechanism for trend analysis or historical querying.

1.2 Research Problem and Motivation

The central research problem addressed by this project is: How can a zero-cost, offline-capable digital management system be designed and deployed to unify fragmented dormitory administration records in a resource-constrained institutional setting, while maintaining full alignment with existing institutional policy and enabling structured data exchange with an external student information system?

The project was motivated by three specific gaps identified through direct administrative experience:

  1. Data fragmentation — student identity, room assignment, bedding purchase, key issuance, and clearance status resided in separate files with no linkage, requiring manual cross-referencing for routine decisions.
  2. Policy compliance drift — handbook policy values (curfew times, fine amounts, notice periods) were either not recorded in operational tools or entered inconsistently across files, with no authoritative default.
  3. Cross-system reporting friction — submitting structured incident data to SARRA2 for citizenship point processing required transcribing information from physical records into a separate interface, introducing errors and delays of one to three days per submission cycle.

Section 2 — Research Methodology & System Design

2.1 Methodology: Design-Based Research

This project employed a design-based research (DBR) methodology, a recognized approach in educational technology and information systems research in which the researcher is simultaneously the designer, implementer, and evaluator of the artefact under study. DBR is particularly suited to institutional settings where practical deployment constraints shape theoretical design decisions and where iterative refinement in response to real use is the primary mode of validation.

The development proceeded through four iterative phases over six weeks:

Phase Modules Developed Period Key Design Decisions
1 — Core Operations Room Reservations, Student Profiles, Floor Plan, Utilities & Billing, Reports May 2026 localStorage data layer; SheetJS bundled offline; BroadcastChannel sync; emptyStudent() factory pattern
2 — Records & Reference Room Inspection, Key Inventory, Inventory, Dean's User Guide, APIU Handbook May 2026 IndexedDB for photos; A4/A5 CSS print layouts; Code 39 SVG barcode generation
3 — Student Affairs & Staff Nightly Attendance, Incident Reports, Student Admin, Dorm Workers, Staff Scheduling, Maintenance June 2026 APIU Handbook policy grounding; SARRA2 CSV protocol; mobile-first RA interface; BF-016 DormDB compliance

2.2 Architectural Design Decisions

Three foundational constraints shaped the system architecture:

  1. Zero external dependencies during operation. The system must function with no internet access, no server infrastructure, and no cloud subscription. This ruled out server-side databases (PostgreSQL, MySQL), cloud SaaS platforms, and framework-based front-ends requiring npm build pipelines. The solution: vanilla JavaScript ES6+ with all third-party libraries (SheetJS v0.20.2) bundled inline in the HTML file.
  2. Cross-module data consistency. When a student's name changes in Room Reservations, that change must be immediately visible in Student Profiles, Attendance, Reports, and Clearance. The solution: a single shared data API (dorm-db.js) with typed localStorage keys, getter/setter pairs, and a BroadcastChannel event bus that notifies all open browser tabs within one second of any data change.
  3. Policy-grounded defaults. Configurable values (curfew times, fine amounts, notice periods) must default to the values specified in the APIU Residence Hall Handbook (2017) to prevent policy drift. The solution: all default values are seeded from documented handbook sources and are visible in Settings tabs within each module.

2.3 Data Model Design

The central data model object (emptyStudent(room)) defines 18 fields per bed slot covering identity, reservation status, period flags, move-out tracking, room hold, storage rental, transfer history, clearance form, and enrollment semester. A companion ensureStudent(s) function provides backward compatibility: any record loaded from an older Excel export or localStorage snapshot is merged against the current field definitions before being written back, preventing null-reference errors in downstream rendering functions.

The shared semester registry (dormSemesterCfg localStorage key, introduced in Phase 4) stores a list of named semesters with start/end dates and a pointer to the current semester. This single registry propagates to all 16 modules via DormDB.on(SEMESTER_CFG, handler) subscriptions, replacing 7 previously isolated semester text fields that had caused cross-module filter mismatches when semester labels were entered inconsistently.

Section 4 — Scholarly Significance, Future Research & Attestation

4.1 Scholarly Significance

This project contributes to several intersecting areas of applied scholarly inquiry:

  1. Educational technology in under-resourced institutional contexts. The system demonstrates that fully functional, multi-module institutional software can be built and deployed at zero licensing and infrastructure cost using browser-native technologies. This is particularly significant for small or mission-driven universities (such as APIU) where commercial dormitory management software (typically $300–$1,200 USD per year) is cost-prohibitive or unavailable in a locally-compliant form.
  2. Offline-first design for intermittent connectivity environments. The architecture — localStorage persistence + IndexedDB photo storage + BroadcastChannel real-time sync + inline-bundled third-party libraries — provides a reproducible design pattern for institutional software that must operate reliably in settings where internet connectivity is intermittent or absent.
  3. Policy knowledge engineering in software defaults. The approach of encoding institutional policy values (handbook curfew times, fine schedules, notice periods) as verified, versioned default values in software configuration — rather than leaving them to ad hoc staff interpretation — represents a practical model for reducing compliance drift in academic residential settings.
  4. Cross-system integration protocol design without API coupling. The SARRA2 integration protocol (CSV export from DormPortalUniversal, manual import into SARRA2) provides a reproducible pattern for lightweight inter-system data exchange between institutional platforms that do not share a technical infrastructure, avoiding the complexity and cost of API development while maintaining structured, auditable data transfer.

4.2 Limitations

  • Single-device data model: Data is stored on the Dean's device. Multi-user concurrent editing is not supported. The BroadcastChannel sync works across tabs on the same device only.
  • No server-side backup: Data loss is possible if the device is lost or fails without a recent JSON export backup. Mitigation: regular "Export All Data" reminders documented in the User Guide.
  • Time estimation: The operational time savings reported in Section 3.3 are estimates based on practitioner observation, not a controlled study with pre/post measurement. A formal time-and-motion study would strengthen these claims.
  • Scalability: The localStorage ceiling (~5–10 MB) limits the system to approximately 200–300 active students with photos. For larger dormitories, a cloud-backed architecture would be required.

4.3 Future Research Directions

  • Controlled pre/post study measuring administrative time savings with statistical rigor
  • Extension to multi-user (server-backed) architecture for larger dormitory contexts
  • Generalization of the SARRA2 CSV protocol to a standards-based data exchange format (e.g., SIF, Ed-Fi) for broader institutional interoperability
  • Comparative study of offline-first vs. cloud-first institutional software in intermittent-connectivity environments
  • Student satisfaction study measuring perceived administrative responsiveness before and after deployment
